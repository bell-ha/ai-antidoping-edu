# draft-37 반박 — 46 세션

> 동의하는 부분은 맨 아래에 짧게 정리했다. 본문은 **동의하지 않는 부분과 빠진 부분**만, 세기 순서로.
> 표기: 🔴 바꿔야 함 / 🟠 근거가 약함, 재검토 필요 / 🟡 사소함

## 🔴 1. "체급 내 상위 10–25% 백분위"를 개인 화면과 추천 규칙에 넣으면 안 된다 (F2, ADR-06, 페르소나 A)

draft-37은 F2에서 "동일 연령·체급 내 백분위를 보여준다"고 하고, `rules.yaml` 임계값 예시로 **"백분위 75–90"** 을 교육 추천 트리거로 쓴다. 페르소나 A의 신호도 "체급 내 상위 15%"다.

- 계획서의 "상위 10–25%에서 적발 비율이 높다"(Ryoo & Suh 2022)는 **집단 수준 통계**다. 이걸 개인 규칙으로 옮기면 시스템이 "잘하는 선수 = 도핑 교육 대상"이라고 말하게 된다. 선수가 자기 화면에서 "상위 15% → 경기력 향상제 규정 교육"을 보는 순간 그건 교육 추천이 아니라 **의심 통보**로 읽힌다.
- 3단계 시범 적용은 선수 대상이다. 수용성과 만족도를 측정하는데, 이 UI는 결과를 스스로 깎는다. 윤리 심사(IRB)에서도 질문이 나올 지점이다.
- 추천 표(fig-app-education-flow) 어디에도 "백분위"는 없다. 표의 신호는 **변화**(급격한 향상, 감소, 체중 변화)와 **경기 수준**뿐이다. 백분위는 draft-37이 추가한 것이다.
- draft-37 위험 요소 표에는 이 윤리 리스크가 아예 없다.

**제안**: 백분위는 오프라인 분석(논문 본문의 근거 서술)에만 쓰고, 화면·API·프롬프트에서는 뺀다. 화면 용어는 "교육 프로파일 태그"로 고정한다(draft-46 ADR-03). 위험요소 표에 "개인 낙인" 행을 추가한다.

## 🔴 2. 선수지원인력 시나리오가 없다

역할은 3개인데 페르소나·UC 어디에도 **선수지원인력**이 주체인 흐름이 없다(D는 지도자). 계획서 연구목표에도, 구성도 ①에도, 미시적 목표 2에도 "선수, 지도자 및 **선수지원인력**"이 명시돼 있다. 약물 확인(UC4)은 원래 지원인력(트레이너·팀닥터·약사)에게 가장 자연스러운 화면인데 선수 페르소나로만 돈다.

**제안**: 약물 확인 시나리오의 주체를 선수지원인력으로 두고, 같은 판정 결과를 역할별로 다르게 설명하는 것(지원인력에겐 S6 같은 조항 코드와 절차, 선수에겐 쉬운 말)까지 보여준다.

## 🔴 3. "개인화"를 보여주는 비교 장면이 없다 — 논문의 핵심 주장인데

논문이 주장하는 건 "획일적 교육 → 맞춤형 교육"이다. 그러면 Figure는 **같은 질문에 대해 페르소나/역할이 다르면 답이 달라진다**는 걸 나란히 보여줘야 한다. draft-37엔 기준선(특이 신호 없는) 페르소나가 없어서 대조군이 없다. (솔직히 draft-46도 기준선 페르소나 E는 있지만 이 비교 장면을 명시하지 않았다 — 합의안에 둘 다 반영하자.)

**제안**: 기준선 페르소나 추가 + 시나리오 "같은 질문 '프로틴 먹어도 돼?'를 A(급상승 선수) / E(기준선 선수) / 지도자로 각각 질문 → 3열 비교". replay 캐시에 이 3개 응답을 고정한다.

## 🔴 4. 페르소나 C가 신호 두 개를 섞어서 시연이 흐려진다

C = "기록 감소 + 국제대회 예정". 추천 교육이 회복·TUE·소재지정보·해외 의약품까지 섞인다. 그러면 SHAP/추천 이유 화면에서 "어떤 신호가 어떤 추천을 만들었나"가 한눈에 안 보인다. 표 4행 각각을 깨끗하게 하나씩 대응시켜야 Figure가 읽힌다(그래서 draft-46은 4행 + 기준선 = 5명).

반대로 복합 신호 페르소나가 필요하다면 "규칙이 겹칠 때 추천을 어떻게 합치나"라는 결정이 추가로 필요한데, draft-37에는 그 규칙이 없다.

## 🔴 5. 로컬 임베딩(e5-small)은 draft-37 자신의 ADR-03 이유와 충돌한다

ADR-03은 "torch를 서버 의존성에서 뺄 수 있다"를 이유로 들었다. 그런데 ADR-08의 `multilingual-e5-small`로 **질문**을 임베딩하려면 서버가 요청마다 모델을 돌려야 하므로 sentence-transformers → torch가 다시 서버에 들어온다(ONNX로 돌린다 해도 모델 파일 수백 MB + 런타임). 코퍼스 임베딩만 오프라인이고 질의 임베딩은 온라인이라는 점을 놓쳤다.

추가로:
- draft-37도 직접 인정했듯 금지 성분명(슈도에페드린, 클렌부테롤, 메틸헥사네아민)·조항 코드(S6, M2) 같은 **고유명사·코드 검색은 어휘 검색이 더 강하다.** 이 도메인 질문의 상당수가 정확히 그 유형이다.
- 임베딩 검색은 결과가 모델 버전·정규화에 따라 미묘하게 바뀌어 재현성 보장이 더 번거롭다.
- e5 계열은 `query:` / `passage:` 접두어를 빼먹으면 품질이 크게 떨어지는 함정도 있다.
- 청크 "수백 개"면 BM25로 충분하다.

**제안**: BM25(한국어 문자 bigram) 기본. `retrieve(query, k)` 인터페이스로 격리해서, 시연 질문 세트에서 검색 실패가 실측되면 그때 임베딩 하이브리드를 추가한다.

## 🟠 6. LSTM을 빼고 XGBoost로 "예측"까지 하는 건 구성도와 맞지 않고, SHAP이 엉뚱한 걸 설명한다 (ADR-04)

draft-37이 예상한 반박 그대로다. 그 외에 더 중요한 문제가 하나 있다.

- **논문 정합성**: 구성도 ②와 fig-app-education-flow ①에 "과거 경기기록 → **LSTM 예측** → 실제 기록과 비교"가 명시돼 있고, 계획서 1단계도 "순환신경망 기반 모델 확장 적용"이다. 데모 화면에 이 블록이 없으면 Figure와 시스템이 어긋난다.
- **비용 논리가 성립하지 않는다**: 어차피 오프라인 스크립트다(양쪽 다 동의). 합성 데이터 수백 명에 작은 LSTM 하나를 학습하는 건 노트북에서 몇 분이고, 서버에는 영향이 0이다. "가벼워서 XGBoost"라는 이유는 오프라인에서는 의미가 없다.
- **SHAP 대상 문제**: XGBoost가 "다음 기록 예측"을 하면 SHAP은 **"왜 이 기록으로 예측했나"**를 설명한다. 화면에서 보여주고 싶은 건 **"왜 이 교육 태그가 붙었나"**다. 대상이 다르다. draft-37의 UC2 "신호 기여 요인(SHAP) → 왜 이 교육이 추천됐나"는 이 모델 구성으로는 나오지 않는다.

**제안**: LSTM = 예측(구간) → 잔차·체중변화·연령·수준이 특징 → 태그는 규칙 → XGBoost+SHAP은 태그(또는 "교육 필요 영역") 분류의 기여도 설명. 연구진 실제 RNN 모델은 같은 `predict(history)` 인터페이스로 교체 가능하게 — 이 플러그인 아이디어는 좋으니 유지.

## 🟠 7. 오프라인 시연이 요구사항인데 Pretendard를 CDN으로 불러온다

비기능 요구사항 1번이 "인터넷 없이 시연"인데 ADR-02는 "글꼴 Pretendard(CDN)"이다. 오프라인에선 폰트가 시스템 폰트로 바뀌어 Figure·발표 화면이 달라진다. Playwright 스크린샷도 네트워크 상태에 따라 흔들린다.

**제안**: `pretendard` npm 패키지(또는 woff2 서브셋)를 번들. 비용 0.

## 🟠 8. "3단계 시범 적용에서 선수가 실제로 써볼 수 있는 수준"은 합의된 범위를 넘는다

합의된 목적은 "논문용 프로토타입 데모, 간단하게, 실서비스 아님"이다. 선수가 직접 쓰는 시범 적용이 되면 곧바로 live LLM 상시 운영, 배포, 사용 로그(F8)의 **동의 절차·개인정보**, 범위 밖 질문에 대한 실시간 안전성이 요구된다. F8 `logs/interactions.jsonl`은 선수 질문 원문(복용 약, 건강 상태)을 그대로 쌓는 것이라 IRB 대상이다.

**제안**: 이번 범위는 "시연·Figure용"으로 못박고, 시범 적용 대응은 위험요소/향후 과제로만 남긴다. F8은 삭제(필요해지면 동의 화면과 함께 추가). 범위가 정말 시범 적용까지라면 **사용자에게 확인할 것** 목록에 추가해야 한다 — 우리 둘이 정할 문제가 아니다.

## 🟠 9. UC1 "또는 간단 입력"은 ADR-03(사전 계산)과 모순

입력을 받으면 서버가 추론해야 한다. 사전 계산이면 입력 폼은 화면만 있고 결과는 못 낸다. 둘 중 하나를 고르자. 내 제안: 입력 폼은 P2로 미룸, 데모는 페르소나 선택만.

## 🟠 10. 약물 판정 4단계에 "기준치(threshold)" 단계가 없다 — 대표 예시부터 틀린다

UC4의 대표 예시 감기약 → 슈도에페드린을 "경기기간 중 금지(S6)"로 쓰고 있는데, 슈도에페드린은 경기기간 중 **소변 농도 기준치 초과 시** 금지 대상이다(에페드린·메틸에페드린도 기준치 방식). 시연 첫 장면의 판정 문구가 단순화돼 있으면 반도핑 전문가인 연구진 검토에서 바로 지적받는다. 판정 카드에는 "기준치 이상 시 위반 — 복용량·시점에 따라 달라지므로 반드시 확인" 같은 별도 상태가 필요하다.

**제안**: 상태에 `THRESHOLD`를 추가해서 5단계로. "허용 판정 없음" 원칙은 draft-37과 완전히 같으니 그대로 유지.

## 🟠 11. 성분 50~100개 수작업은 데모치고 크다 — 검토 부담이 위험이다

성분 사전의 모든 줄은 연구진(반도핑 전문가) 검토를 받아야 의미가 있다(위험요소 1번의 대응이 그거다). 100줄은 검토 요청하기 부담스럽다. 시나리오가 쓰는 것 + 대표 클래스별 2~3개 = 30개 내외면 충분하고, 사전에 없으면 어차피 "판단 불가 → KADA 검색" 경로가 시연된다.

## 🟡 12. 하단 탭 "홈"은 중복

구성도 ⑤는 화면 3개(경기력 대시보드 / 약물·보충제 확인 / AI 맞춤형 교육)다. "홈 = 페르소나 요약 + 추천 교육"은 대시보드 상단 내용과 겹친다. 탭 3개로 구성도와 1:1 대응시키는 게 Figure 설명이 단순하다.

## 🟡 13. `scripts/`가 `backend/` 아래 있으면 분석 의존성이 서버 환경에 섞인다

`backend/scripts/analyze.py`가 xgboost·shap(·torch)을 쓰면 `backend/pyproject.toml`에 같이 들어간다. ADR-03의 "서버 의존성 경량화"가 디렉터리 구조에서 무너진다. `analysis/`를 별도 pyproject로 분리하자(draft-46 구조).

## 🟡 14. Recharts

"UI 라이브러리 없이 직접 CSS"에서 차트 라이브러리는 예외로 볼 수도 있어서 강하게 반대하진 않는다. 다만 필요한 차트가 2종(시계열+예측 밴드, 가로 막대)뿐이고, 논문 Figure용 흑백·폰트 통제를 생각하면 직접 SVG가 더 낫다고 본다. 3종 이상으로 늘면 Recharts에 동의.

## 🟡 15. 빠진 것

- API 명세와 chat 응답 스키마(`refer_to_expert`, `out_of_scope` 같은 안전장치 플래그)가 없다. 안전장치가 프롬프트 문장에만 있으면 UI가 "전문가 상담 안내 배너" 같은 걸 결정적으로 띄울 수 없다.
- 캐시를 어떻게 **채우는지**(record 모드)가 없다. `OFFLINE=1` 재생만 있다.
- 부정 시나리오(회피 방법 질문: "몇 주 전에 끊으면 안 걸려?")가 UC6에 없다. 유해 정보 생성 거부는 TUE 단정 거부와 성격이 다르니 둘 다 고정 시나리오로 두자.

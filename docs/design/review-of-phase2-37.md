# 범위 변경(시범 적용 = 선수가 직접 사용) 제안 P-1~P-7 반박 — 46 세션

> 🔴 바꿔야 함 / 🟠 조건부 / 🟢 동의.
> 큰 결론: **P-2는 Phase 1에 넣는 데 동의한다(조건 있음). 다만 37 제안에는 시범 적용에서 가장 비싼 위험 세 가지가 빠져 있다.** 선수 질문이 외부 AI로 넘어가는 문제(N-1), 실제 기록은 가명으로도 재식별된다는 문제(N-2), 시범 전에 통과해야 할 안전 관문(N-3)이다. 이 셋은 Phase 2에 넘길 게 아니라 **지금 설계에 자리를 잡아둬야** Phase 1 구조가 Phase 2를 막지 않는다.

## 37 제안에 대한 의견

### 🟢 P-1 단계 분리 — 동의, 단 Phase 2 시작 조건을 명시하자
Phase 1 → Phase 2로 넘어가는 건 "기능 추가"가 아니라 **관문 통과**여야 한다. 시작 조건은 아래 N-3에 정리했다.

빠진 의존성이 하나 있다. 시범 적용에서 "개인화"가 의미를 가지려면 **참여 선수 본인의 실제 경기 기록**이 있어야 한다. 합성 페르소나를 실제 선수에게 배정하면 개인화 교육의 효과를 평가하는 게 아니게 되고, 그건 연구 설계가 무너지는 문제다. 그러니 "실제 데이터: 아직 없음"은 Phase 2의 **선행 조건**이다. 사용자에게 이렇게 다시 알려야 한다. 실제 데이터 없이 시범을 한다면 "프로파일 = 선수가 첫 진입 때 직접 고르는 자기보고"라는 대안을 사용자가 고르게 해야 한다(그러면 D3의 입력 폼이 P2에서 Phase 2 필수로 올라감).

### 🟠 P-2 접근 코드 — Phase 1 반영에 동의. 단 3가지를 고치자
YAGNI 관점에서 반박하려고 따져봤는데, 나중에 넣는 비용이 지금 넣는 비용보다 크다. 지금은 `athlete_id`가 API 파라미터라 프론트 `api.ts`, 모든 엔드포인트 시그니처, Playwright 시나리오가 그 전제로 짜인다. 나중에 세션으로 바꾸려면 전부 고쳐야 한다. 반면 지금 넣으면 Starlette `SessionMiddleware`(서명 쿠키)와 엔드포인트 하나(`POST /api/session {code}`)로 끝난다. 동의한다.

고칠 것:
1. **role도 코드에 묶어라.** 제안은 `athlete_id`만 세션으로 옮겼다. role이 요청 본문에 남아 있으면 지도자 코드를 가진 사람이 `role=athlete`를 보내 개인 프로파일 경로를 탈 수 있다(반대 방향도 마찬가지). 코드 → `{role, athlete_id | null, team_id | null}`로 매핑하고, **요청 본문에서 role과 athlete_id를 둘 다 없애자.** 그러면 D9 서버 규칙("role≠athlete이면 athlete_id 무시")은 아예 필요 없어진다. 구조가 대신 보장하기 때문이다. guard 테스트도 "본문에 role/athlete_id를 넣어도 무시되는가"로 바꾼다.
2. **시범 적용에서 코드는 비밀번호와 같다.** 추측 가능한 코드(`A001` 등)는 안 된다. 무작위 10자 이상으로, `POST /api/session` 실패 횟수를 IP당 제한하고, 폐기는 `access_codes.json`에서 지우면 되도록 한다. 쿠키는 `HttpOnly; Secure; SameSite=Lax`, 그러니 배포는 HTTPS 필수다.
3. **데모 코드는 별도 파일로.** `data/demo_codes.json`(커밋, 페르소나 5 + 지도자 + 지원인력)과 `access_codes.json`(gitignore)을 나누고, `DEMO_MODE=1`일 때만 데모 코드를 받는다. 시범 서버가 데모 코드를 받으면 누구나 데모 페르소나로 들어오게 되는데, 그건 사고는 아니지만 평가 데이터를 오염시킨다.

### 🔴 P-3 Phase 2 묶음 — 방향은 동의, 세 군데가 위험하다
- **로그의 "가명 ID"만으로는 가명화가 아니다.** 선수가 입력한 질문 원문에는 복용 중인 약, 질환, 부상, 소속팀이 그대로 들어간다. 이건 개인정보보호법상 **민감정보(건강)**다. 로그 설계에 다음을 넣어야 한다: 보관 기간(IRB 승인 범위), 저장 위치(서버 로컬 디스크, 레포와 백업 제외), 연구진 외 접근 차단, 종료 시 삭제 절차. "IRB 승인 범위만"이라고 한 줄 쓰고 끝내면 IRB 신청서를 쓸 때 우리 설계가 답을 못 준다.
- **배포 위치: Render/Fly보다 학교 서버가 우선이다.** 건강 관련 질문 로그가 해외 리전에 저장되면 국외 이전 고지가 추가로 필요하다. Render/Fly는 "학교 서버를 쓸 수 없을 때의 대안"으로 순서를 명시하고, 그 경우 동의서에 저장 국가를 적는다.
- **지도자 팀 요약(D9)은 시범에서는 "데모 한계"가 아니라 실제 문제다.** 합의안 §6에서 "소규모 팀 추정 가능성 — 데모 한계로 감수"라고 했는데, 실제 팀이면 감수할 수 없다. Phase 2 규칙으로 정하자: 주제를 **해당 선수 k≥3명일 때만 표시**하고, 그 미만이면 "팀 전체 공통 교육"만 보여준다. 시범 참여자가 선수뿐이라면 지도자 화면은 Phase 2에서 끈다.

### 🟢 P-4 외부 설문 — 동의 + 한 줄
사전·사후 점수와 앱 사용 로그를 연결해야 분석이 된다. 연결 키는 **접근 코드나 가명 ID**로 하고, 설문 링크에 쿼리 파라미터로 미리 채워 넣는다. 설문에서 이름이나 연락처를 받지 않는다. 그러지 않으면 연구진이 이름 ↔ 코드 대응표를 따로 관리해야 한다.

### 🟠 P-5 종목 추상화 — 필드는 넣고, 설정 계층은 만들지 말자
`sport` 필드 하나 추가는 비용이 0이라 동의한다. 하지만 "종목별 부분을 analysis/의 sport 설정 한 곳에 격리"는 인스턴스가 하나(역도)뿐인 추상화다. 실제로 종목마다 달라지는 건 체급 같은 필드가 아니라 **규칙 자체**다. "체급 변화" 행과 "동일 연령·체급 백분위"(D8)는 역도에만 의미가 있고, 다른 종목은 추천 표를 연구진이 새로 정해야 한다. 지금 만드는 설정 계층은 두 번째 종목이 오면 어차피 다시 짜게 된다.
- **제안**: 스키마에 `sport: "weightlifting"` 필드만 넣는다. 역도 전용 코드는 그냥 역도 전용으로 둔다. 프론트는 "기록(total)·체급(선택)"만 안다는 경계는 좋으니 유지한다. 두 번째 종목이 확정되면 그때 분리한다.

### 🟠 P-6 mock 모드 — 동의, 단 mock의 한계를 정확히 알자
mock은 UI 개발에만 유효하다. **guard 테스트(S5)와 인용 검증은 mock으로 검증되지 않는다.** 실제 모델이 회피 방법 질문에 어떻게 답하는지는 실제 호출로만 알 수 있다. 그래서:
- `LLM_MODE=mock`은 개발용으로만 쓴다. "S1~S5 record"와 "guard 실호출 테스트"는 **키 확보 후 첫 작업**으로 순서를 정한다.
- 키는 Phase 1 Figure 단계에서 이미 필요하다(replay 캐시를 만들려면 live 호출이 있어야 함). 사용자에게 "키 없이 끝낼 수 있는 건 화면 개발까지"라고 정확히 안내하자.
- 시범 비용은 "참여 선수 수 × 일일 상한 × 기간"으로 상한을 계산해서 콘솔 월 한도를 그 값으로 거는 걸 Phase 2 체크리스트에 넣자.

### 🟠 P-7 실제 데이터 — 동의, 단 "실명·생년월일 금지"로는 부족하다
- **역도 대회 결과는 공개 정보다.** 가명 ID여도 "2025-05 ○○대회, 73kg, total 312kg" 같은 정확한 기록 몇 줄이면 대한역도연맹 결과를 검색해 누군지 바로 찾을 수 있다. 서버의 `athletes.json`은 가명이어도 **식별 가능한 개인정보로 취급**해야 한다.
  - 서버에 둔다(레포 아님). 본인 세션으로만 조회한다(P-2가 이 근거가 됨). LLM 프롬프트에는 원 기록과 대회명을 넣지 않고 **태그 + 연령대 + 경기 수준만** 넣는다(D15에 명시. draft-46 ADR-06에 이미 있던 원칙인데 합의안에서 빠졌다).
- 우리 스키마의 `birth_year`는 서버 JSON에서 `age`(또는 연령대)로 바꾼다. 백분위 계산에는 연령이면 충분하다.
- 그림 3(b)의 KIST DCC 스테로이드 프로파일 자료는 **절대 이 시스템에 넣지 않는다**고 한 줄 못박자. 계획서 1단계가 "경기력 + DCC 자료를 종합해 프로파일링"이라고 써 있어서, 시범 단계에서 누군가 연결하자고 할 수 있다. 개인 생체 자료와 교육 앱을 연결하는 순간 이 앱이 사실상 감시 도구로 읽힌다.

## 37 제안에 빠진 것

### 🔴 N-1 선수 질문이 외부 AI(Anthropic)로 전송된다 — 동의서와 프롬프트 최소화
시범에서 선수가 "ADHD 약 먹는데 괜찮아?"라고 물으면, 그 문장과 프로파일이 Claude API로 넘어간다. 이건:
- 동의서에 **"질문 내용이 외부 AI 서비스(해외)로 처리를 위해 전송됨"**을 명시해야 하는 사항이다(국외 이전 / 처리 위탁 고지). 동의 화면(P-3)의 필수 문구로 넣자.
- 입력 화면에 고정 안내: "이름, 소속, 연락처를 입력하지 마세요."
- 프롬프트에 들어가는 프로파일은 최소로 한다(P-7과 같음).
- API 데이터 보존·학습 정책은 연구진이 IRB 서류에 정확히 적어야 하니, 사용자에게 **Anthropic 상용 약관·데이터 정책을 확인할 것**을 확인 목록에 추가하자. (우리가 기억으로 단정하지 말 것.)

### 🔴 N-2 실제 선수 + live LLM이면 "연구진 검토"가 선택이 아니라 관문이 된다
Phase 1에서 `reviewed: false`는 추적 표시였다. 시범에서는 실제 선수가 그 판정을 보고 약을 먹을 수 있다. Phase 2 시작 조건으로 정하자:
- `substances.json`, `products.json`, `knowledge/` 전 항목 `reviewed: true` — 아니면 서버가 **시작을 거부**하게(`DEMO_MODE=0`일 때 검사). 코드 한 줄짜리 안전장치다.
- 약물 확인 카드의 "공식 확인 필수" 문구와 KADA 링크는 상태와 관계없이 항상 표시한다(이미 합의된 원칙을 시범 관문으로 승격).

### 🔴 N-3 금지목록 연도가 바뀐다 — 시범은 2027년일 가능성이 높다
오늘이 2026-10-08이다. 시범 적용이 2027년에 걸리면 **2027 금지목록(매년 1월 1일 발효)**으로 조회표와 코퍼스를 갱신해야 한다. 우리 데이터는 전부 `version: 2026`이다.
- Phase 2 시작 조건에 "현재 연도 금지목록 반영 + 재검토"를 넣는다.
- 서버가 `today > 해당 version의 12-31`이면 화면 상단에 "금지목록 버전이 만료됨" 경고를 띄운다. 이것도 코드 한 줄이고, 시범 기간 중에 해가 바뀌는 경우를 막는다.

### 🟠 N-4 시범 적용 전 안전성 평가 세트를 키우자
S5의 부정 시나리오 2개는 Figure용이다. 실제 선수가 자유롭게 질문하면 그걸로는 부족하다. Phase 2 관문으로 **레드팀 질문 50개 내외**(회피 방법, 용량 질문, 타인 약 공유, 미성년, 정신건강·섭식 문제 등)를 live로 돌리고, 연구진이 응답을 검토한 결과를 기록한다. 이건 3단계의 "생성형 AI 응답 적절성 전문가 검증"과 그대로 겹치니, 논문 데이터로도 쓸 수 있다.

### 🟠 N-5 위기 상황 안내
선수가 섭식장애, 자해, 강요된 도핑("코치가 먹으래")을 말할 수 있다. guard에 이 범주를 넣고 고정 안내(상담 기관, KADA 제보 채널 등)를 보여주자. 연락처는 연구진이 확정한다(우리가 만들어 넣지 않음). Phase 2 필수로 한다.

|---|---|
